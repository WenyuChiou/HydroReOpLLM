Compatibility filenames are retained.

**Fig. 1. Structure and daily operational workflow of HydroReOpLLM.** Rule-based and LLM decision agents provide alternative release requests to shared reservoir calculations. Optional knowledge supplies additional operating knowledge to Prompt construction. The Valid reply? diamond represents Response validation: parsing the reply and checking its structure and basic numerical values. Yes carries the validated release request to Reservoir operation. The second Requested release link supplies the same request to Operating-rule check. Retry or stop on the No branch means another attempt is made if allowed by the configured retry limit; otherwise the simulation stops before the reservoir update. Retried replies are validated again; the internal retry loop is omitted from this overview. Reply validity does not establish compliance with operating rules. Operating-rule check uses the release proposal, date, inflow, storage at the start of the day, and configured operating limits; its criteria are specified for each application. Operating-rule check is required in the illustrated application and finishes before the physical update without automatically modifying or vetoing the request. Trace records retain the LLM decision inputs, model replies, release requests, and any operating-rule check results. The Inflow branch supplies the same inflow used by Reservoir operation. Storage carries updated storage to the next step, and Release + spill denotes implemented controlled release plus spill routed downstream. Card colors indicate function: gray, information and its preparation; blue, physical calculations; orange, decision generation; teal, checks and records. Pale frames indicate grouping; the dashed border identifies Optional knowledge. Illustration colors have no additional categorical meaning. P, precipitation; T, temperature; PET, potential evapotranspiration; GWLF, Generalized Watershed Loading Functions; LLM, large language model. ABCD / GWLF denotes alternative rainfall–runoff models.

## Application boundary

The saved LLM demonstrations replay a precomputed daily inflow series; they do not rerun rainfall–runoff at every decision. The package also supports the native stepwise interface. Each application must document its driver, information timing and routing checks.

The illustrated application requires Operating-rule check. The generic interface permits configurable auditors, and rule-based agents can also use checks and trace records. Diagnostic FAIL/WARN/UNKNOWN results do not automatically change or veto a release; check execution errors stop execution. The drawing shows information dependencies, not asynchronous execution.

Retry or stop summarizes configured recovery from eligible reply failures. Retried replies are validated again. If no valid reply is obtained and no further attempt is allowed, the simulation stops before the current reservoir update; no automatic rule-based release is implied. Provider-specific retry and fallback settings are documented in [LLM modules](../LLM_MODULES.md#retry-and-fallback-boundary).
